| 17  | PW error-code numbering scheme                                | Four-digit `PW####` codes grouped by component in 100-blocks: foundation `0001–0099`, config `0101–0199`, worktree-context `0201–0299`, registry `0301–0399`, allocator `0401–0499`, env-resolution `0501–0599`, CLI `0601–0699`, library runtime `0701–0799`, `0801+` reserved. | 19  | Registry lock timeout configurability                         | `PORTWEAVE_LOCK_TIMEOUT_MS` env var overrides the default retry budget (100 × 25ms = 2.5s). Env-var only at v0 — no CLI flag. Non-positive / non-integer values fall back to the default.                                                                                                                                                                                     | Established by [.ai/specs/registry-storage/registry-storage.md](./specs/registry-storage/registry-storage.md). Lock budget is a stress-test knob, not a user-facing setting; env-var keeps the CLI surface small at v0 and avoids a flag that callers would copy-paste and forget about.                                                                                                                                                                                                                        |
| 20  | Tempfile naming and sibling-cleanup window                    | Atomic registry writes use `<path>.tmp.<pid>.<Date.now()>` then `fs.rename`. On each load, sibling tempfiles matching `<basename>.tmp.*` older than 60s are removed.                                                                                                                                                                                                          | Established by [.ai/specs/registry-storage/registry-storage.md](./specs/registry-storage/registry-storage.md). `pid+timestamp` avoids collisions if two writers ever raced past the lock (defense in depth); 60s is long enough for a slow disk to finish a write, short enough that crashed-writer tempfiles do not accumulate across multiple invocations.                                                                                                                                                    |
| 21  | Port-allocator pool range and override                        | Default pool range is `[30000, 60000)` (30,000 candidate ports). `PORTWEAVE_POOL_RANGE="<start>-<end>"` overrides the default; malformed, non-integer, or inverted values fall back silently to the default (same precedent as `PORTWEAVE_LOCK_TIMEOUT_MS`). Pool boundaries are env-only at v0 — no CLI flag.                                                                | Established 2026-05-26 by [.ai/specs/port-allocator/port-allocator.md](./specs/port-allocator/port-allocator.md). 30k–60k leaves headroom past common defaults (Docker, Postgres, Redis below 30k) and stays below the OS ephemeral-port range upper bound. Silent fallback matches the lock-timeout convention so the env-var surface stays consistent.                                                                                                                                                        |
| 22  | Port-allocator block-search direction                         | Block search is **ascending** from the low end of the pool. The first contiguous block of `slotCount` ports that avoids every occupied port is returned.                                                                                                                                                                                                                      | Established 2026-05-26 by [.ai/specs/port-allocator/port-allocator.md](./specs/port-allocator/port-allocator.md). Predictable and debuggable — boardflip's "low offsets first" intuition carries over without surprise. Revisit if observed wear concentrates on the low end of the pool (currently no signal that this matters).                                                                                                                                                                               |
| 23  | Port-allocator service-group ordering                         | Within a contiguous allocation block, services that share a `group` label are reordered to be adjacent in the resulting `ports` map (per the `orderServicesForAllocation` algorithm). Groups appear in first-occurrence order from the source config; ungrouped services retain their original position relative to the groups.                                               | Established 2026-05-26 by [.ai/specs/port-allocator/port-allocator.md](./specs/port-allocator/port-allocator.md). The config loader does not enforce group-adjacency in the services array; the allocator re-derives it deterministically so dual-port services like Kinesis plain + Kinesis TLS always move together across reallocations.                                                                                                                                                                     |
| 24  | `.portweave/.gitignore` auto-creation                         | On first creation of `.portweave/` inside a project, `env-resolution#ensurePortweaveDir` writes `.portweave/.gitignore` containing `*\n` using the `wx` flag so an existing `.gitignore` is never overwritten.                                                                                                                                                                | Established 2026-05-26 by [.ai/specs/env-resolution/env-resolution.md](./specs/env-resolution/env-resolution.md). Matches CLAUDE.md's "runtime state is gitignored" guidance. The `wx` flag makes the operation safely idempotent — repeated runs neither error nor clobber whatever the user later puts in the file.                                                                                                                                                                                           |
| 25  | `.env` overrides only Portweave-known keys                    | When merging a project's `.env` into the computed env map, only keys that Portweave would have computed (envVar plus discoveryEnv entries) are subject to override. Unrelated `.env` keys are NOT forwarded by `resolveEnv` — they pass through whatever existing dotenv loader the user's stack already uses.                                                                | Established 2026-05-26 by [.ai/specs/env-resolution/env-resolution.md](./specs/env-resolution/env-resolution.md). Keeps `.portweave/current.env` scoped to Portweave's allocation surface; avoids accidentally re-emitting unrelated secrets a user already manages elsewhere.                                                                                                                                                                                                                                  |
| 26  | Discovery URL templates use allocated port                    | `${serviceName}` templates in `discoveryEnv` always resolve against the _allocated_ port for that service, even when the corresponding envVar is overridden via the project's `.env`. Per-key overrides do not transitively reshape derived URLs.                                                                                                                             | Established 2026-05-26 by [.ai/specs/env-resolution/env-resolution.md](./specs/env-resolution/env-resolution.md). Overrides should be explicit per-key, not propagate through templates — otherwise a single `.env` override of `API_PORT=4000` would silently rewrite every URL that references `${api}`, which is surprising and rarely what the user actually wants.                                                                                                                                         |
| 27  | Banner output stream = stderr                                 | All `[portweave]` banner lines go to `io.stderr`, not stdout.                                                                                                                                                                                                                                                                                                                 | Established 2026-05-26 by [.ai/specs/run-command/run-command.md](./specs/run-command/run-command.md). Child stdout pipelines (`portweave run -- generate-data \| jq`) must not be polluted by portweave diagnostic output. Stderr is the conventional stream for tool diagnostics; both DESIGN.md Appendix B and the feature doc specify this. Verbose mode prints unredacted filesystem paths; `--verbose=safe` mode is the future mitigation for CI path-disclosure concerns.                                 |
| 28  | `--config` and `--count` are mutually exclusive               | Passing both `--config <path>` and `--count <n>` to `portweave run` is `CLI_INVALID_FLAGS` (PW0601) and returns exit code 1.                                                                                                                                                                                                                                                  | Established 2026-05-26 by [.ai/specs/run-command/run-command.md](./specs/run-command/run-command.md). `--config` selects named-service mode; `--count` selects anonymous mode (synthesizes `PORT_1..PORT_N`). The two modes are mutually exclusive — allowing both would require an ambiguous merge of two config sources.                                                                                                                                                                                      |
| 29  | Exit-code translation rules for `portweave run`               | `null exitCode + signal` → `128 + signal-number` (POSIX: SIGINT=130, SIGTERM=143). Spawn failure → `127` (POSIX command-not-found). Non-zero child exit propagates unchanged. Unknown termination (both null) → `1`.                                                                                                                                                          | Established 2026-05-26 by [.ai/specs/run-command/run-command.md](./specs/run-command/run-command.md). The 128+N formula is the POSIX shell standard and matches boardflip's `scripts/bin/dev.ts` behavior. `127` for spawn failure distinguishes "portweave couldn't start the command" from "command ran and failed."                                                                                                                                                                                          |

| 31  | Library runtime upward-walk config discovery rule             | The runtime library walks from `opts.cwd` (or `process.cwd()`) upward toward the filesystem root to find `portweave.config.json`, stopping at the first hit. This is a runtime-layer addition — the CLI's `loadConfig` reads from a single explicit directory. The walk uses `fs.access` to probe each level; non-ENOENT errors (e.g. EACCES) are rethrown.                   | Established 2026-05-26 by [.ai/specs/library-runtime/library-runtime.md](./specs/library-runtime/library-runtime.md). Vite plugins and Vitest workers can run from arbitrary cwds that are subdirectories of the project root; without upward-walk the user would have to always pass an explicit `configPath`. Walking stops at the nearest ancestor so a monorepo with inner configs doesn't accidentally pick up the root config.                                                                            |

Silent fallback is retained for absent/empty env var only.                                            | Established 2026-05-26 by the v0 review-cleanup PR (port-allocator code-review MI-1 + S-1). ## Strategic position (informs §8 and future commercialization discussions)

If Portweave becomes ubiquitous, the position unlocks several adjacent products:

| Adjacent feature                   | Description                                                                                                    | Monetization fit              |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| **Local dev DNS**                  | `http://api.boardflip.dev` resolves to the right localhost port for the current worktree.                      | Free OSS or paid pro          |
| **Cross-project discovery**        | Agent or service A in repo X looks up service B in repo Y on the same machine.                                 | OSS core                      |
| **Team-shared registries**         | "Brian's local stack is reachable at these tunneled endpoints." Tailscale-adjacent.                            | **Paid team tier**            |
| **Web UI / dashboard**             | "What's running on my machine? Click to open."                                                                 | Paid pro tier                 |
| **Service-definition marketplace** | "Install the Postgres preset," "install the Redis cluster preset."                                             | Marketplace economics         |
| **Agent orchestration substrate**  | Coding agents spawn/discover/cleanup dev servers via Portweave. Becomes the de facto agent coordination layer. | OSS core; possibly enterprise |
| **Enterprise dev environments**    | Replaces the "developer onboarding wiki." Compliance, audit, SSO.                                              | **Enterprise SaaS**           |
| **IDE plugins**                    | VS Code / JetBrains panels for "what's running, click to open."                                                | Paid pro                      |

**Monetization playbook (proven elsewhere — Sentry, Vercel, Tailscale, Linear):**

- Free OSS core (CLI, registry, single-machine allocation) drives mass adoption.
- Pro tier ($10–20/dev/mo): Web UI, cross-machine sync, dev DNS, IDE plugins, telemetry.
- Team tier ($30–50/dev/mo): Shared service definitions, team-wide observability, audit logs.
- Enterprise: SSO, on-prem registry server, compliance certifications.

**Honest caveats:**

- Local-dev tools have weak enterprise willingness-to-pay unless they hit team-scale pain. Saving an individual dev 10 minutes a week doesn't sell licenses; saving 50 devs from collisions in a shared remote dev cluster does.
- The Pro/Team monetization only kicks in once the adjacent features (DNS, sync, observability) exist — significant additional work beyond v0.
- The OSS wedge has to win first. If the CLI isn't ubiquitous, none of the adjacent products have a customer base. v0 quality matters strategically, not just functionally.
